# Project audit and fix implementation plan

Audit date: 7 October 2026 (Asia/Calcutta). Source baseline: `ad87f08667997683a876ad19c112a191f83f96ac` on local `main` and `origin/main`.

The application is an early single-user MVP. Contacts, drafting, review, sending, replies, and outcomes exist, but core approval and delivery guarantees do not hold. The highest-impact reproduced failures are duplicate delivery, implicit approval, broken resume delivery, disappearing quota counts, and follow-ups sent after a reply.

This document records 52 work items, including confirmed defects, reliability risks found in source, and missing workflows required to support the README. It is the implementation backlog, not a claim that every possible defect has been discovered. All items are **Open** at this audit baseline. No application fixes were made during this audit.

## Scope, evidence, and limits

- Reviewed all 26 tracked files, every Flask route, all repository methods, the composer, sender, reply detector, tracking and QC helpers, dashboard JavaScript/HTML/CSS, configuration, tests, sample CSV, and README.
- Inspected the two untracked scripts without executing them. `rewrite.py` rewrites Git history and is unrelated to application repair. Preserve both scripts and the existing backup branch.
- Existing tests fail during collection: `ModuleNotFoundError: services.state_machine`. Further visible failures are the missing `temp_db` fixture, missing `claim_for_sending`, and incompatible repository constructor calls in the test.
- Ran isolated Python probes using temporary databases. All external sockets are blocked; SMTP, IMAP, and AI are mocked. See [baseline_probe.py](audit/2026-10-07/baseline_probe.py) and [baseline_results.json](audit/2026-10-07/baseline_results.json). The results are observations of baseline behavior, not passing regression assertions.
- The original `outreach.db` content hash was unchanged by the probes. Its private records were not read for this audit. Actual legacy data integrity remains to be checked on a protected snapshot before migrations.
- Python 3.12.10 works with access to its installation. The earlier apparent missing interpreter was a sandbox-access problem; rebuilding the virtual environment is not an established requirement.
- Python source parsing and `node --check static/app.js` pass. `pip check` reports no broken installed requirements. These do not establish functional correctness.
- Ran `pip-audit` in a separate tool environment without modifying application dependencies. Raw output: [dependency_audit.json](audit/2026-10-07/dependency_audit.json). The scanner reports 16 entries across three packages; some are duplicate advisories. Deduplicating by advisory ID yields 10 distinct findings. Reachability and impact vary.
- UI findings are from source review, not an actual rendered-browser/accessibility test. Browser regression checks are mandatory implementation gates below.
- No live email was sent, no mailbox was accessed, and no paid Gemini request was made. Real-provider behavior, quotas, account permissions, and end-to-end delivery remain integration checks. The ignored local release ZIP is a historical artifact, not the source baseline.
- `staging` has unrelated history and release scheduling work. Its source and CI are outside this `main` application audit; do not merge it as a shortcut to fixing the app.

## Required behavior and implementation rules

1. Saving content leaves a draft awaiting review. Approval applies to an exact content revision, recipient, and resume choice. Editing any approved material revokes that approval.
2. Only a valid transition may change status. Sent email history cannot be reapproved or silently rewritten. Every mutation must detect nonexistent records and stale revisions.
3. Each send must atomically claim an approved revision and reserve its quota before contacting SMTP. Two requests or workers must never both submit the same claimed message.
4. SMTP cannot provide a universal exactly-once guarantee across network and process failures. Persist attempt identity and Message-ID before submission. Once acceptance is uncertain, stop automatic retries and expose an `uncertain` result for reconciliation. A successful SMTP submission followed by a database error must never trigger another immediate send.
5. Delivery quotas count accepted sends regardless of later outcomes. Active and uncertain reservations conservatively consume capacity. All date boundaries use one configured timezone; UTC timestamps remain the storage format.
6. Revalidate approval, suppression, follow-up eligibility, send window, quota, and selected resume immediately before submission. Preserve the approved snapshot rather than silently substituting a changed file or recipient.
7. Fresh setup must work without an existing database or hidden manual SQL. Migrations must preserve history, be versioned, and have tested backup/restore instructions.
8. Automated tests use isolated databases and fake providers. Production data, credentials, and recipient addresses must never enter fixtures or CI.
9. Preserve personal/local-only scope. Contact scraping, multi-user teams, and an OAuth transport replacement are optional future projects, not blockers for this repair plan. If remote access is enabled, single-owner authentication becomes required.

## Issue register

P0 means delivery or approval correctness must be repaired before routine sending. P1 means a functional/security/reliability defect or essential regression foundation. P2 means workflow, maintainability, or operational completeness. Evidence marked **reproduced** appears in the baseline JSON; **source** denotes a code-inspection finding; **gap** denotes missing product behavior rather than a proven crash.

## Verification protocol for every fix

1. Reproduce the issue on the current code using a temporary DB and synthetic inputs. Record the failing behavior and issue ID.
2. Add a meaningful regression assertion at the service/API/browser boundary where the defect occurs. For concurrent delivery, use multiple connections/workers and barriers, not just a mocked method return.
3. Implement the smallest coherent change, including its migration if needed. Preserve existing records and do not execute unrelated local scripts.
4. Run the targeted test, adjacent workflow tests and required checks. Inspect persisted status/attempt/events and provider calls, not just HTTP 200 or a success toast.
5. Test negative paths and recovery. A send fix must cover SMTP acceptance plus DB failure and ambiguous transport outcomes; a data fix must cover duplicates and legacy migrations.
6. Update the completion ledger with the real test command, result, commit and remaining integration limits. A code change is **Implemented, unverified** until those checks pass.
7. Run the full suite at phase boundaries and after cross-cutting changes. Do not run live outreach to verify a patch.

Suggested target test modules: `test_config.py`, `test_migrations.py`, `test_contacts.py`, `test_imports.py`, `test_review.py`, `test_sender.py`, `test_send_concurrency.py`, `test_resumes.py`, `test_composer.py`, `test_followups.py`, `test_replies.py`, `test_tracker.py`, `test_api.py`, `test_jobs.py`, and browser scenarios. Names are illustrative; behavior coverage is the requirement.
